In your Bobcat DXP project you built reusable React components across multiple portals. A product list component re-renders every time any unrelated state changes in the parent. Which hook specifically prevents a child component from re-rendering when its props have not changed?

CPass data down through all intermediate components as props (prop drilling) — this is the correct React pattern for sharing data between components regardless of nesting depth
DLift the shared state to the nearest common ancestor component and pass it down as props to the siblings that need it — if the ancestor is far up the tree, wrap with a React Context provider to avoid prop drilling through many intermediate layers

Q07Node.js Event LoopHard
Your Express.js API endpoint calls a synchronous bcrypt.hashSync() to hash a user password before saving to PostgreSQL. Under load, 50 concurrent requests hit this endpoint and responses slow to 30 seconds. What is the root cause and fix?
ANode.js is single-threaded and cannot handle 50 concurrent requests regardless of implementation — the fix is to run multiple Node.js processes using a load balancer
Bbcrypt.hashSync() is CPU-bound and blocks the Node.js event loop — while hashing, Node cannot process any other requests. Fix: use bcrypt.hash() (the async version with callback/promise) which offloads work to libuv's th.
CThe issue is the PostgreSQL INSERT blocking the event loop — replace synchronous pg queries with the async pg Pool client; the bcrypt operation is not the bottleneck
Dbcrypt.hashSync() is slow because it has no database connection pooling — replace it with a connection pool to make the hash operation faster
Q08REST API DesignMedium
In your Synapse platform you designed REST APIs for task management with notification and escalation. A BBVA CMS API needs an endpoint where an editor can publish multiple articles in one action. What is the most REST-appropriate design?
AGET /articles/publish?ids=1,2,3 — GET requests with query parameters are idempotent and safe, making them the correct choice for state-changing operations that should be repeatable
BPATCH /articles/1, PATCH /articles/2, PATCH /articles/3 — individual PATCH calls per article ensure atomicity; batch operations violate REST's resource-per-URL principle
CPOST /publish with a body containing an array of article IDs — REST allows batch operations via POST to a resource action endpoint; semantically, publishing is a state transition, not a CRUD create
DPUT /articles with a body of all articles including their new published:true status — PUT replaces the entire resource collection, making batch state updates semantically correct
Q09Express MiddlewareMedium
For the BBVA CMS API you need to: authenticate every request, log all requests with response time, and validate request bodies against a JSON schema. In what order should these middleware be registered in Express and why?
AAuthentication → logging → JSON schema validation — authenticate first to reject unauthorised requests before spending resources on logging
BJSON schema validation → authentication → logging — validate inputs first to reject malformed requests before any authentication overhead
CLogging → authentication → JSON schema validation — log every request first (even failed ones) for audit trail completeness, then authenticate to reject unauthorised requests early, then validate schema on requests that passed auth
DAll three orders are equivalent — Express evaluates all registered middleware and picks the most efficient execution order at runtime
Q10JWT & Session ManagementHard
In your Synapse platform you implemented role-based access control. For the BBVA CMS with Editor, Reviewer, and Admin roles, what is the correct JWT implementation to prevent a user whose role is downgraded from continuing to use their old token?
AInclude a role_version field in the JWT; increment the version in the database when a role changes; reject JWTs whose role_version doesn't match the current database value
BStore the user's current role in a database table; on every request, query the database to check the live role rather than trusting the role claim in the JWT — the JWT only provides user identity, not authorisation
CBoth A and B are valid production patterns with different trade-offs: A gives immediate revocation at the cost of one DB lookup per request; B gives eventual consistency (up to 15min) with no DB lookup per request — the correct choice depends on BBVA's compliance requirements
DSet a very short JWT expiry (15 minutes) with refresh tokens — downgraded roles take effect within 15 minutes when the short-lived access token expires; the refresh endpoint checks the current role before issuing a new token
Q11Node.js Async PatternsMedium
In your AWS Lambda functions for Bobcat DXP, you call three independent APIs: fetchProductData(), fetchDealerInfo(), and fetchPricingData(). Each takes ~1 second. Written with sequential awaits, total time is ~3 seconds. What is the correct fix?
AUse async/await in a for...of loop — looping over an array of fetch functions with await in a for...of correctly parallelises the calls
BUse Promise.all([fetchProductData(), fetchDealerInfo(), fetchPricingData()]) — this initiates all three Promises concurrently and awaits all three completions simultaneously; total time becomes ~1 second (the slowest call) instead of ~3 seconds
CUse setTimeout with 0ms delay between each call — this defers each API call to the next event loop tick, allowing them to interleave
DMove two of the three calls to separate Lambda functions and invoke them in parallel — Node.js cannot run concurrent network calls within one Lambda execution

Q12PostgreSQL Query OptimizationHard
In your Synapse platform you optimized PostgreSQL schemas and stored procedures. A BBVA CMS query filtering articles by status='published' AND created_at > '2024-01-01' AND author_id = 42 on a 2M-row table takes 8 seconds. What indexing strategy helps most?
ACreate a compound index on (author_id, status, created_at) — equality filters (author_id, status) first, range filter (created_at) last. PostgreSQL uses the leftmost prefix for equality matches and pushes the range filter to the end, covering all three conditions in one index scan
BAdd a B-tree index on status alone — the query planner will use this index for the status filter and apply the other conditions as post-filter on the matched rows
CPartition the table by created_at into monthly partitions — partitioning eliminates the full-table scan by pruning irrelevant partitions, replacing the need for any additional indexes
DAdd a full-text index on the status column — full-text indexes are optimised for equality lookups on string columns and will accelerate the status filter
Q13MongoDB vs PostgreSQLMedium
You have used both MongoDB and PostgreSQL. For the BBVA CMS storing financial product pages where each page has a fixed schema (title, rate, terms, category) but content editors occasionally add custom fields that vary per product type, which database and schema strategy fits best?
ATwo databases: PostgreSQL for fixed fields and MongoDB for custom fields, joined at the application layer using the product ID as the key — this gives both databases the workload they are optimised for
BPostgreSQL with a JSONB column for custom fields — the fixed fields (title, rate, terms, category) are typed columns with constraints and indexes; custom fields live in a JSONB column that is schema-flexible, queryable, and indexable.
CPostgreSQL with EAV (Entity-Attribute-Value) pattern — store all custom fields in a separate attribute table with rows per field; this is the standard PostgreSQL pattern for variable schema in relational databases
DMongoDB — its schema-less design handles custom fields natively without migrations; each document can have any additional fields an editor adds without affecting other products
Q14Redis Usage PatternsMedium
In your Bobcat DXP project using AWS Lambda, you need to cache API responses for 5 minutes to reduce downstream API calls. Redis is available. Which Redis pattern and command correctly implements read-through caching with expiry?
AUse Redis SETEX with a fixed key per endpoint — SETEX sets a value and expiry atomically, but each Lambda cold start must call SETEX regardless of whether a value exists, causing unnecessary cache overwrites on every invocation
BUse Redis RPUSH to append each API response to a list and LRANGE to retrieve the last response — lists preserve order and allow you to keep a history of responses
CUse Redis HSET to store responses as hash fields keyed by endpoint path — hashes group related cache entries and are more memory-efficient than separate string keys for multiple endpoints
DUse Redis GET to check for a cached value; if missing (cache miss), fetch from the API, then SET the response with EX 300 (5-minute TTL). On subsequent requests, GET returns the cached value until TTL expires — this is the cache-aside (lazy loading) pattern
Q15Database TransactionsHard
In the BBVA CMS, publishing an article requires: (1) update article status to published, (2) create an audit log entry, (3) increment the author's published_count. If the server crashes between steps, data is inconsistent. How do you implement this atomically in PostgreSQL with Node.js?
AUse a distributed saga pattern — publish a 'publish article' event to a message queue, have separate microservices handle each step asynchronously, and implement compensation events if any step fails
BUse PostgreSQL stored procedures — stored procedures run all steps inside the database engine where crashes cannot interrupt them, providing automatic atomicity without application-level transaction management
CRun the three UPDATE/INSERT statements sequentially with separate await calls — if any fails, catch the error and manually run compensating queries to reverse the completed steps
DWrap all three operations in a PostgreSQL transaction using the pg library: BEGIN → UPDATE article → INSERT audit_log → UPDATE author count → COMMIT. If any step throws, call ROLLBACK — all three operations succeed together or none do

Q20AWS Lambda CMSMedium

Q22API Caching StrategyMedium
Your BBVA CMS public-facing API serves financial product data that changes daily. 10,000 users hit the same /api/products/mortgage endpoint repeatedly. How do you reduce load without serving stale financial data for more than 1 hour?

BUse database query caching by enabling PostgreSQL's shared_buffers and work_mem — PostgreSQL caches frequent query results in memory, reducing query execution time without any application-level cache layer
