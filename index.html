You integrated Redux across 20+ APIs in your inventory app. A component subscribes to a Redux slice via useSelector. When does that component re-render, and how do you prevent unnecessary re-renders?

Q06Next.js SSR vs CSRMedium

AgetServerSideProps — fetches data on every request, so visitors always get fresh content. Trade-off: slower TTFB since data is fetched before each render
BgetStaticProps — static pages are built at deploy time and never update until the next deployment
CUse useEffect to fetch data in the browser on every page visit — this is the fastest approach

Q07Express MiddlewareMedium
In your Node.js backend you handle 20+ REST APIs. What is Express middleware and how does the order of middleware registration affect a request?
AMiddleware is only used for authentication — it does not affect other types of requests
BOrder of middleware registration does not matter — Express evaluates all middleware simultaneously and picks the most specific match
CMiddleware is a function with (req, res, next) that runs in the middleware stack. Order matters: middleware registered first runs first. If a middleware does not call next(), the request stops there — subsequent middleware and route handlers never execute. This is critical: if you register a route handler before an authentication middleware, the auth check is bypassed for that route
DMiddleware runs after the route handler completes — it post-processes the response
Q08REST API DesignMedium
You built REST APIs for inventory operations. A client reports that calling POST /items repeatedly with the same data creates duplicate records. What API design principle prevents this, and how do you implement it?
AUse GET instead of POST for creating records — GET requests cannot create duplicates
BAdd a unique index on the items collection in MongoDB — the database will reject duplicates automatically
CIdempotency: a repeated identical request produces the same result as a single request. Implement with: (1) client sends a unique Idempotency-Key header with each request, (2) server stores processed keys in a cache/DB, (3) if the key was already processed, return the stored response without re-executing. POST is inherently non-idempotent; this pattern adds idempotency artificially
DAdd a 1-second server-side delay between requests — this prevents duplicates from simultaneous calls
Q09Node.js AsyncMedium
Your Express API fetches data from MongoDB, sends an email notification, and logs the operation — all for one request. Written naively with await in sequence, this takes 900ms. How do you optimise this?
AIf the email and log operations do not depend on each other, run them in parallel: const [dbResult] = await Promise.all([fetchFromMongo(), sendEmail(), logOperation()]). Operations that are independent should never be awaited sequentially
BMove all database operations to a separate Node.js process using child_process.fork()
CUse setImmediate() — it runs all promises simultaneously
DUse setTimeout(fn, 0) to push each operation to the next event loop tick — this makes them run faster
Q10GraphQL vs RESTMedium
You listed GraphQL in your tools. A frontend developer complains that the REST inventory API returns 50 fields per item but the product listing page only needs 5 fields, causing slow responses. How does GraphQL specifically solve this?
AGraphQL compresses the JSON response automatically, making it smaller than REST
BGraphQL caches all responses in the browser, so subsequent requests are faster even with all 50 fields
CGraphQL allows the client to filter results server-side using WHERE clauses in the query string
DGraphQL eliminates over-fetching: the client specifies exactly which fields it needs in the query, and the server returns only those fields. query { items { id name price } } returns only those 3 fields, not all 50. It also solves under-fetching (N+1 problem) by allowing nested queries that fetch related data in one request instead of multiple REST calls
Q11Authentication & JWTMedium
Your apps implement role-based authentication. In a JWT-based auth system, when a user logs in you return a JWT. How do you handle the case where a user's role changes (e.g. admin privileges revoked) while their token is still valid?
ADelete the token from the client's localStorage — the server will automatically deny subsequent requests
BA JWT is stateless — once issued, the server cannot invalidate it until it expires. Options: (1) Use short-lived access tokens (15 min) + a refresh token system; revoking access means invalidating the refresh token. (2) Maintain a token blocklist/blacklist in Redis — check every request against it. (3) Embed a version number in the JWT; store the current version in DB; reject tokens with old version numbers
CJWTs include the user's live role from the database — they always reflect the current role
DJWT tokens automatically refresh from the server every 5 minutes — role changes are picked up automatically

Q12MongoDB AggregationHard
In your Cold Storage app you generate reports on stock movement. You need to calculate total inward stock per product per warehouse for the last 30 days. Which MongoDB feature handles this efficiently?
AUse the MongoDB Aggregation Pipeline: $match (filter last 30 days), $group (group by productId + warehouseId, sum the quantity), $sort (optional). This runs entirely in MongoDB — no data is sent to Node.js before aggregation. It is faster and uses far less memory than fetching all documents and aggregating in JavaScript
BCreate a MongoDB view that pre-computes the totals — views update automatically when data changes
CUse MongoDB's mapReduce function — it is the only way to perform multi-field grouping
DUse MongoDB's find() with a JavaScript forEach loop in Node.js to calculate totals in memory
Q13MongoDB Schema DesignMedium
Your inventory system tracks stock items, each with a category, supplier, and multiple warehouse locations. MongoDB is schema-less but schema design still matters. When do you embed documents vs use references (like SQL foreign keys)?
AAlways embed all related data in one document — MongoDB performs best with no references
BEmbed when: data is frequently read together, the embedded data belongs exclusively to the parent, and the embedded array will not grow unboundedly (e.g. embed an item's last 5 status changes). Reference (store ObjectId) when: data is shared across multiple documents (a supplier referenced by thousands of items), the related data is large or grows without bound, or you need to query the related data independently
CAlways use references for all relationships — embedding causes data duplication
DEmbedding is only supported for arrays with fewer than 10 items — use references for larger datasets
Q14MongoDB IndexingMedium
Your inventory search runs queries on the items collection filtering by warehouseId AND productCategory AND filtering by inwardDate range. The collection has 200,000 documents and queries are slow. What indexing strategy helps?
ACreate a compound index on the fields used in the query in the correct order: db.items.createIndex({ warehouseId: 1, productCategory: 1, inwardDate: -1 }). MongoDB can use the leftmost prefix of a compound index — so it can also serve queries on just warehouseId, or warehouseId + productCategory. Equality fields should come before range fields in a compound index
BAdd a single-field index on each of the three fields separately — MongoDB will combine them automatically
CAdd a text index on all string fields — MongoDB text indexes handle all query types
DUse MongoDB Atlas Search — standard indexes do not improve filter query performance
Q15Database TransactionsHard
In your warehouse system, a Stock Transfer operation moves 100 units from Warehouse A to Warehouse B. This requires: decrement stock in A AND increment stock in B. If the server crashes between the two operations, the stock count is wrong. How do you prevent this in MongoDB?
AUse MongoDB multi-document transactions (supported since MongoDB 4.0 with replica sets): start a session, run both update operations within session.withTransaction(), and commit. If either operation fails, the entire transaction rolls back atomically — both updates succeed together or neither does
BUse MongoDB's $inc operator — it is atomic and handles multi-document updates automatically
CRun both operations inside a try/catch block — if either fails, log the error and retry manually
DPerform both updates in a single MongoDB updateMany() call — this is automatically atomic across documents

Q16CMS ArchitectureMedium
The BBVA CMS project requires content editors to update financial product pages without deploying code. How does a headless CMS architecture differ from a traditional CMS, and why is it more suitable for a Next.js frontend?
AHeadless CMS is only suitable for blogs — it cannot handle structured financial product data
BA traditional CMS (e.g. WordPress) tightly couples content storage with the presentation layer — the CMS also renders the HTML. A headless CMS (e.g. Contentful, Sanity, Strapi) stores content and exposes it via APIs (REST or GraphQL) — the presentation is completely separate. For a Next.js app: the CMS manages content, Next.js fetches it via API and renders it. Editors update content in the CMS UI; the Next.js frontend regenerates via ISR or webhooks — no deployment needed
CA headless CMS removes the database layer — content is stored in flat files instead
DA headless CMS is the same as a traditional CMS but without a login page
Q17Role-Based Access ControlHard

The backend check is the real security

Q19Frontend SecurityHard
The BBVA CMS displays financial content that includes user-submitted rich text (editors can include HTML). A malicious editor injects into an article. When a viewer opens the article, the script runs and steals their session. What is this attack and how do you prevent it?
AThis is Cross-Site Scripting (XSS). Prevent it by: (1) never using dangerouslySetInnerHTML with unsanitised user content in React, (2) sanitising all HTML before storing or rendering using a library like DOMPurify (strips dangerous tags/attributes), (3) implementing a Content Security Policy (CSP) header that blocks inline scripts, and (4) using HttpOnly and Secure flags on cookies so JavaScript cannot read them
BThis is a CSRF attack. Prevent it by adding a CSRF token to every form submission
CThis is a man-in-the-middle attack. Prevent it by using HTTPS everywhere
DThis is SQL injection. Prevent it by using parameterised queries in your MongoDB operations
Q20State Management StrategyMedium
The BBVA CMS has: (1) global auth state (user, role, token), (2) server data (articles fetched from API that can go stale), (3) UI state (modal open/closed, active tab). A colleague says 'put everything in Redux.' What is the better architecture and why?
ASplit by concern: global auth state → Redux (persists, shared everywhere). Q21Error HandlingMedium
Your inventory Express.js backend throws unhandled promise rejections in async route handlers, causing the Node.js server to crash. What is the correct pattern to handle errors in async Express routes?
AUse process.on('unhandledRejection') to catch all async errors globally and send a response
BWrap every route handler in a global try/catch that catches all errors before they reach the route
CCreate an asyncHandler wrapper: const asyncHandler = fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next). Wrap every async route with it. When an error is thrown, it is passed to next(err), which triggers Express's error middleware (app.use((err, req, res, next) => ...)). Centralise error formatting and HTTP status codes in the error middleware
DAdd async: true to the Express route definition — this enables built-in async error handling
Q22API PaginationMedium
Your inventory API returns all 50,000 stock records in one response. The frontend freezes and the response takes 8 seconds. What pagination strategy do you implement, and what are the trade-offs between offset pagination and cursor pagination?
AReturn all records but compress the response with gzip — this makes large responses acceptable
BOffset pagination (page=2&limit=20): easy to implement with MongoDB skip/limit, supports jumping to any page. Problem: slow on large collections (MongoDB still scans skipped documents) and inconsistent results if records are inserted/deleted between page requests. Cursor pagination (cursor=lastItemId): uses the last item's ID as a pointer — next query fetches items after that ID. Fast on large collections (uses the _id index), consistent results, but cannot jump to arbitrary pages
COffset and cursor pagination are identical in performance — choose based on UI preference only
DUse WebSockets to stream all 50,000 records continuously — the frontend renders them as they arrive
Q23MERN DeploymentMedium
You are deploying the BBVA MERN application to production. The React frontend, Node.js/Express backend, and MongoDB are currently all on one VM. What are the risks of this architecture and how should production deployment be structured?
ARisks: single point of failure (one VM crash takes down everything), cannot scale services independently (frontend gets more traffic than backend — you cannot scale just the backend), no resource isolation (a memory leak in Node.js competes with MongoDB's RAM). Production architecture: frontend → static hosting (Vercel, Netlify, or CDN). Backend → containerised (Docker) on a managed platform or Kubernetes. MongoDB → managed service (MongoDB Atlas). Each scales independently and failures are isolated
BSingle-VM deployment is the recommended production architecture — it simplifies network communication between services
CThe main risk is that MongoDB and Node.js use the same port — configure them on different ports to fix this
DSingle-VM is fine for production as long as the VM has enough RAM and CPU — architecture separation is only needed for enterprise applications
