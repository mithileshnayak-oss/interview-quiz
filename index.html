Q01SCCsJD: SCCsHard
A pod on OpenShift fails with is forbidden: unable to validate against any security context constraint. The pod spec sets runAsUser: 1000. What is the correct remediation sequence?
AIdentify the minimum-privilege SCC the workload needs, then bind it to the pod's service account via oc adm policy add-scc-to-user <scc> -z <sa> -n <ns>. Never assign privileged unless genuinely required
BRemove runAsUser: 1000 from the pod spec — OpenShift auto-assigns UIDs and custom UIDs are unsupported
CSet allowPrivilegeEscalation: true in the pod securityContext — this bypasses SCC UID validation
DAssign the privileged SCC to the default service account — the fastest fix for SCC admission errors
Q02OLM / OperatorsJD: Operators/OLMHard
You need to install a community Operator into namespace my-app (not openshift-operators). What is the correct OLM resource sequence and what does OperatorGroup control?
ACreate a namespace-scoped OperatorGroup in my-app with targetNamespaces: [my-app], then create a Subscription in the same namespace. OperatorGroup defines the Operator's watch scope — without it OLM rejects the Subscription
BApply the Operator YAML directly with oc apply — OperatorGroup is only required for cluster-scoped operators
COperators can only be installed into openshift-operators — namespace-scoped OLM installs are unsupported
DInstall via helm install — OLM cannot target restricted namespaces
Q03MachineConfigJD: MachineConfigHard
You need to push net.ipv4.tcp_max_syn_backlog=4096 to all worker nodes on an on-premises OpenShift cluster. What resource do you use, and what happens to nodes after you apply it?
ACreate a ConfigMap in kube-system — the node agent reads it automatically
BCreate a MachineConfig targeting the worker MachineConfigPool. MCO applies it by draining and rebooting each worker node in a rolling sequence — cordoned, updated, then uncordoned
CRun an Ansible playbook against all workers via SSH — MachineConfig only manages RHCOS image updates
DDeploy a DaemonSet with an init container running sysctl -w — the standard Kubernetes pattern

ATLS termination requires Istio Gateway — native Routes do not support custom certificates

Q05Certificate RotationJD: Cert RotationHard
An on-premises OpenShift cluster's internal certificates expire in 5 days. What is the native auto-rotation mechanism and what are two common causes of failure?
ARedeploy the cluster — in-place renewal is not supported
BManually regenerate with openssl — OpenShift does not auto-rotate certificates
CInstall cert-manager — the only supported rotation mechanism on OCP 4.x
DOpenShift cluster Operators auto-rotate internal certs via the cluster CA. Q06Disconnected UpgradeJD: Air-GappedHard
You are upgrading an on-premises OCP 4.13 cluster to 4.14 in a disconnected environment. What must be prepared before running the upgrade command?
AMirror the 4.14 release images to the internal registry using oc-mirror, update the ImageContentSourcePolicy or ImageDigestMirrorSet, then run oc adm upgrade --to-image <mirrored-digest>. Without this the upgrade fails immediately with image pull errors

Q07Workload IdentityJD: GCP IAMHard
A GKE pod needs to write to Cloud Storage without a service account key file. What is the correct GCP-native approach and why is it preferred?
AMount the GCP service account JSON key as a Kubernetes Secret — Kubernetes encrypts secrets at rest
BSet GOOGLE_APPLICATION_CREDENTIALS to a mounted key file path — standard GCP authentication
CAssign the Storage Admin role to the GKE node pool's default service account — pods inherit the permissions
DUse Workload Identity: annotate the Kubernetes ServiceAccount with iam.gke.io/gcp-service-account and bind it to the GCP SA. Pods receive short-lived tokens automatically — no key file to rotate, leak, or commit to Git

A GKE private cluster (no public node IPs) needs pods to pull images from Docker Hub. What GCP feature enables outbound internet for private nodes?
AUse a LoadBalancer Service with externalTrafficPolicy: Local — this enables node-level egress
BConfigure Cloud NAT on the VPC subnet — it provides outbound internet via SNAT for instances without public IPs. For production, also consider mirroring images to Artifact Registry to eliminate the runtime internet dependency
CEnable Cloud CDN on the VPC — it caches Docker Hub images at GCP PoPs and serves them to private nodes
DPrivate clusters cannot pull from Docker Hub — all images must be baked into node OS images
Q09Cost OptimisationJD: Resource OptimisationMedium
GKE cluster costs doubled. kubectl top nodes shows 8% average CPU utilisation. Which combination of actions most directly addresses this?
ASwitch to GKE Autopilot — it always costs less than Standard mode
BDelete idle namespaces — they still consume node capacity
CUpgrade to a larger machine type — bigger nodes are more cost-efficient per CPU

Q10NetworkPolicy EgressJD: Network PoliciesHard
Pods in namespace frontend must only egress to pods in namespace backend on port 8080, and be blocked from all other destinations. Which describes the correct NetworkPolicy structure?
ANetworkPolicy with policyTypes: [Egress], podSelector: {} (all frontend pods), egress: [{to: [{namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: backend}}}], ports: [{port: 8080}]}]. A single egress rule with no other rules implicitly blocks all remaining egress
BCreate a GCP VPC firewall rule allowing port 8080 between the two subnets
CUse Istio AuthorizationPolicy — Kubernetes NetworkPolicy does not support cross-namespace egress filtering
DSet policyTypes: [Ingress] on the backend namespace — GKE only supports ingress rules for cross-namespace traffic

Q11GitLab CI PipelineJD: GitLab CIHard
A GitLab CI pipeline must build → test → scan → deploy, but deploy only when BOTH test AND scan pass AND only on the main branch. What keyword combination enforces this?
AUse needs: [test, scan] on deploy (explicit DAG dependency — fails if either upstream fails) combined with rules: [{if: '$CI_COMMIT_BRANCH == "main"'}]. needs: is more explicit than stage ordering and supports cross-stage dependencies
BUse when: manual on deploy — a human approves after reviewing results
CUse allow_failure: false on test and scan — this propagates failures to all downstream jobs
DAdd only: [main] to deploy — GitLab automatically blocks it when any earlier stage fails
Q12ArgoCD DriftJD: ArgoCD GitOpsHard
ArgoCD auto-sync is enabled. A developer manually patches a Deployment causing OutOfSync. What happens next, and how do you handle fields legitimately managed outside Git (e.g. HPA-managed replicas)?
AArgoCD never reverts manual changes — OutOfSync only sends a notification
BOutOfSync is permanent until resolved by a Git push — auto-sync only applies to new Application installs
CWith auto-sync enabled, ArgoCD reverts the cluster to Git state. For fields managed outside Git: use ignoreDifferences with jqPathExpressions targeting spec.replicas (for HPA) or controller-managed annotations. Also configure syncOptions: [RespectIgnoreDifferences=true]
DDelete and recreate the ArgoCD Application — the recommended recovery for drift
Q13Helm vs KustomizeJD: Helm & KustomizeMedium
When would you choose Kustomize over Helm for managing dev/staging/prod differences, and what is Kustomize's core structural concept?
AKustomize doesn't support multi-environment deployments — use separate Git branches per environment
BKustomize is only for single-environment deployments — Helm handles multi-environment config better in all cases
CKustomize wraps helm template and stores rendered output in Git — it is a Helm post-processor
DKustomize uses a base + overlays pattern: define base manifests once, then per-environment overlay directories patch only the differences (replicas, image tags, resource limits). Choose Kustomize for plain YAML in Git without templating overhead — ArgoCD applies overlays natively
Q14Zero-Downtime DeployJD: Zero-DowntimeMedium
In a GitOps flow via ArgoCD, what Deployment strategy achieves zero-downtime and what are its two critical application requirements?
AUse RollingUpdate with maxUnavailable: 0 and maxSurge: 1. Two critical requirements: (1) the app handles SIGTERM gracefully within terminationGracePeriodSeconds, and (2) the new version is backwards-compatible with the old during the overlap window — no breaking DB schema changes
BSet maxUnavailable: 100% and maxSurge: 100% — creates all new pods before deleting old ones
CUse Recreate — terminates old pods cleanly before starting new ones
DUse Recreate with a PodDisruptionBudget — PDB prevents all pods being terminated simultaneously

Q15Terraform State LockJD: Terraform from scratchHard
Two engineers simultaneously run terraform apply on the same workspace. What can happen and what is the prevention mechanism?
AConcurrent applies can corrupt the state file — both engineers read stale state, apply divergent changes, last write wins, leaving state inconsistent with actual infrastructure. Fix: remote backend with state locking (S3 + DynamoDB, GCS with locks, or Terraform Cloud). The lock atomically prevents a second apply while the first runs
BTerraform detects concurrent applies and queues the second run — no configuration needed
CUse separate terraform workspace per engineer — separate workspaces have separate state files
DRun terraform apply -lock=false to skip locking — this prevents deadlocks when two engineers run simultaneously
Q16Terraform Module DesignJD: Reusable modulesMedium
Hrishabh built reusable Terraform modules. Which three principles best characterise a well-designed module?
ACombine all resources into one large module to reduce the number of terraform apply runs
BUse count and for_each everywhere; avoid variables.tf — hardcoded values are more predictable
CSingle responsibility (one module = one logical resource group), typed variables with descriptions and validation blocks, and pinned version references (?ref=v1.2.0 not main) so upstream changes don't silently break consumers
DStore state locally within the module — remote state adds complexity
Q17Ansible RolesJD: Ansible rolesMedium
The JD requires writing Ansible roles from scratch. What is the purpose of the handlers/ directory and what is its key efficiency behaviour?
AHandlers are error-handling tasks that run when main tasks fail — the Ansible equivalent of try/catch
BHandlers run before main tasks to pre-configure dependencies — the Ansible equivalent of init containers
CHandlers are tasks triggered by notify. Key behaviour: no matter how many tasks notify the same handler in one play, it runs exactly once at the end — preventing multiple restarts when several config tasks all notify restart nginx
DHandlers run in parallel with main tasks — they offload non-critical operations to reduce playbook time
Q18Terraform DriftJD: IaCHard
A cloud engineer manually added a GCP firewall rule via the Console. Terraform state doesn't reflect this. What does terraform plan show and what are the two options to resolve it?
Aterraform plan shows no changes — Terraform compares code to state file only, not actual cloud resources
BAfter terraform refresh, plan shows the manual rule as a pending destroy (exists in cloud but not in code). Two options: (1) terraform import the rule and add it to HCL — makes it IaC-managed; (2) delete the rule from cloud and recreate via Terraform. Never apply without reviewing the plan
CRun terraform state push — this updates the state to match cloud without changing resources
DDelete the state file and re-import everything — drift is best resolved with a full state rebuild

Q22RHCOS PatchingJD: Air-Gapped PatchingMedium
The security team requires weekly OS patching of RHCOS nodes without internet egress. Why does dnf update fail, and what is the correct patching workflow?
AUse Ansible to push RPM packages via SSH — RHCOS uses rpm-ostree layering that accepts Ansible-managed package overlays

Q23SLO ComponentsJD: Define SLOsHard
The JD requires you to define SLOs, not just consume dashboards. Define SLI, SLO, and Error Budget and explain how they relate operationally.
ASLOs are only relevant for external-facing services — internal platform components like the Kubernetes API server do not need SLOs
BSLI: quantitative measure of service behaviour — e.g. proportion of requests completing under 200ms. SLO: target for the SLI over a window — e.g. 99% of requests under 200ms over 30 days. Error Budget: allowed unreliability — 99% SLO = 1% budget = 7.2 hours/month. When exhausted, feature work pauses and reliability takes priority
CSLI = the Grafana panel; SLO = the Prometheus alert threshold; Error Budget = allowed 5xx errors per day
DSLI = service uptime percentage; SLO = the SLI rounded to two decimal places; Error Budget = remaining uptime before breach
Q24PromQL Error RateJD: PrometheusHard
Write the PromQL expression that alerts when HTTP 5xx error rate exceeds 1% of total requests over the last 5 minutes, per service.
Ahttp_requests_total{status="500"} > 0.01
Bsum(rate(http_requests_total{status=~"5.."}[5m])) by (service) / sum(rate(http_requests_total[5m])) by (service) > 0.01 — rate() handles counter resets; by (service) gives per-service granularity; threshold 0.01 = 1%
Ccount(http_requests_total{status=~"5.."}) / count(http_requests_total) > 0.01
Dincrease(http_requests_total{status=~"5.."}[5m]) > 1
Q25Alert FatigueJD: Define AlertsMedium
The on-call team receives 200+ alerts per night causing fatigue and missed real incidents. What three structural Prometheus/Alertmanager changes fix this without missing real incidents?
AIncrease all alert thresholds — higher thresholds mean fewer alerts
BRoute all alerts to email — less disruptive than PagerDuty
CAdd for: 5m to all alert rules (eliminates transient spikes); alert on SLO burn-rate instead of individual infrastructure metrics (replaces 20 alerts with 1 meaningful one); configure Alertmanager group_by and inhibit_rules (suppress downstream alerts when a root-cause alert is already firing — e.g. suppress all pod alerts when a node is NotReady)

Q26EFK vs LokiJD: Log AggregationMedium
Hrishabh deployed EFK Stack. What is the primary operational challenge of Elasticsearch at high log volume, and what is a common alternative architecture?
AElasticsearch is not open source — it requires a paid Red Hat subscription on OpenShift

Q27RBAC DesignJD: RBACMedium
A developer should view Pods and Deployments in namespace app-prod but not create/delete, and must have no Secrets access. What RBAC resources do you create?
AAssign the built-in view ClusterRole — it grants read-only access to most resources

CCreate a namespace-scoped Role in app-prod with rules for pods and deployments with verbs: [get, list, watch]. Omit secrets entirely — RBAC is deny-by-default. Bind via namespace-scoped RoleBinding. The built-in view ClusterRole (C) includes Secrets access, violating the requirement

Q28Secrets in GitOpsJD: Secrets ManagementHard
Kubernetes Secrets are base64-encoded. A GitOps flow requires storing secrets in Git. What are two production-grade approaches, and what does each encrypt?
AStore secrets as environment variables in GitLab CI/CD settings — they are never written to Git
B(1) Sealed Secrets: encrypt with the cluster's public key into SealedSecret CRDs safe to commit to Git — only the cluster controller can decrypt. (2) External Secrets Operator: store values in AWS Secrets Manager / GCP Secret Manager / Vault; ExternalSecret CRDs reference the external path — the actual value never touches Git
CUse a private Git repository — base64 in private repos is secure since only authorized engineers have access

Q29Production IncidentJD: Prod Incident RCAHard
50% of GKE pods enter CrashLoopBackOff after a config-only change. What is your diagnostic sequence in the first 5 minutes?
AMinute 1-2: kubectl describe pod <crashing> — exit code and last state. Minute 2-3: kubectl logs <pod> --previous — what does the app print on crash? Minute 3-4: compare the changed ConfigMap/env vars via Git diff. Minute 4-5: if root cause found — rollback; if not — rollback first, investigate after. Communicate status at minute 2, not after full diagnosis
BCheck Prometheus CPU and memory metrics — CrashLoopBackOff is always caused by resource exhaustion
CImmediately roll back — investigating wastes time when rollback is always fastest
DDelete all crashing pods — Kubernetes reschedules them and they may succeed on a different node
