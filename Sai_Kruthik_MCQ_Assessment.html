BClickHouse always uses a bloom filter on timestamp regardless of ORDER BY — single-column timestamp queries are always fast
CThe query runs instantly because ClickHouse stores a separate time-series index for all timestamp columns automatically
DPerformance is identical whether querying by service_name or timestamp — MergeTree indexes all columns equally
Q09Materialized ViewsHard
You use a ClickHouse Materialized View to pre-aggregate per-service error rates every 5 minutes. A bug is introduced in the aggregation logic. What happens to data already processed by the broken Materialized View?
AClickHouse automatically re-runs the Materialized View over historical data when you fix and recreate it — past aggregations are corrected automatically
BData already inserted and aggregated by the broken view is permanently incorrect — Materialized Views in ClickHouse process data at INSERT time and do not reprocess historical rows. Fix requires: drop the broken MV, truncate the target table, fix the MV definition, recreate it, and backfill by re-inserting or re-reading historical data from the source table
COnly future inserts use the new MV definition — existing aggregated data is frozen but accurate because it was computed correctly at the time of insert
DALTER MATERIALIZED VIEW automatically reprocesses all historical data to apply the corrected logic
Q10TTL & PartitioningMedium
ConnX needs to retain telemetry data for 90 days and automatically delete older data. Which ClickHouse feature handles this, and what is the correct syntax pattern?
AUse a scheduled Airflow DAG to run DELETE FROM metrics WHERE timestamp < now() - INTERVAL 90 DAY every night — ClickHouse has no native data expiry
BUse ClickHouse's native TTL: add TTL timestamp + INTERVAL 90 DAY DELETE to the table definition. ClickHouse automatically merges and discards expired rows in the background, combined with PARTITION BY toYYYYMM(timestamp) so whole partitions can be dropped efficiently

Q11ClickHouse vs PostgresMedium
ConnX replaced "slower ad-hoc query workflows" with ClickHouse. A query aggregating error counts across 500M rows with a GROUP BY on service name runs in 0.4s in ClickHouse vs 8s in PostgreSQL. What is the primary architectural reason for this difference?
AClickHouse uses more RAM than PostgreSQL, so the entire dataset fits in memory and is faster to scan
BClickHouse uses columnar storage — an aggregation query reading only the service_name and error_count columns reads only those two columns from disk. PostgreSQL row storage reads all columns of every matching row even when only two are needed, causing dramatically higher I/O
CClickHouse uses a B-tree index on every column automatically, while PostgreSQL requires manual index creation
DPostgreSQL does not support GROUP BY on non-indexed columns — the 8s query was running without an index, not a fair comparison
Q12Schema MigrationHard
You need to add a new Nullable(Float32) column to a 500M-row ClickHouse table in production without downtime. What happens when you run ALTER TABLE metrics ADD COLUMN cpu_pct Nullable(Float32)?
AClickHouse rewrites all 500M rows to include the new column — the table is locked for writes during this operation
BClickHouse's ALTER TABLE ADD COLUMN is a metadata-only operation — it updates the schema definition but does not rewrite existing data parts. New inserts write the column; existing parts return NULL for the new column until they are naturally merged. Zero downtime, near-instant on any table size
CADD COLUMN is not supported on ReplicatedMergeTree — you must recreate the table with the new schema and backfill
DClickHouse queues the schema change and applies it only after all current queries complete — the ALTER blocks for up to 60 seconds

Q13PySpark ShuffleHard
Your PySpark job at SmartIMS joins a 250GB transactions table with a 50MB lookup table. The job takes 45 minutes with a standard join. What optimisation cuts this to under 5 minutes?
AIncrease spark.sql.shuffle.partitions from 200 to 2000 — more partitions always speed up joins
BUse a broadcast join: df_large.join(broadcast(df_small), "id"). Spark broadcasts the 50MB table to all executors, eliminating the expensive shuffle exchange. The 250GB table never moves — only the small lookup is replicated. This is the canonical optimisation for large-table + small-table joins
CCache the 250GB transactions table with df.cache() before the join — cached DataFrames skip the join shuffle
DUse coalesce(1) before the join to reduce to a single partition — less partitions means fewer shuffle operations
Q14Partition SkewHard
A PySpark job processes enterprise logs partitioned by customer_id. One customer has 80% of the data. The job takes 3 hours while 99% of executors finish in 10 minutes. What is this problem and how do you fix it?
AThis is executor starvation — increase the number of executors so each gets less data
BThis is data skew — one partition is disproportionately large, causing one executor to run 18x longer than the others. Fix: salt the skewed key (append a random integer 0–9 to customer_id to create 10 sub-partitions), or use Spark 3.x's Adaptive Query Execution (AQE) with spark.sql.adaptive.skewJoin.enabled=true which automatically splits skewed partitions
CThis is a memory leak — the large customer's data overflows executor memory and causes GC pauses. Fix: increase executor memory
DThis is a driver bottleneck — the driver is serialising all partition results. Fix: use df.repartition(1000) before the aggregation
Q15Airflow IdempotencyHard
An Airflow DAG loads daily sales data into PostgreSQL. Task 4 of 6 writes 50,000 rows. Task 5 fails. On retry, Task 4 runs again. What happens without idempotency design, and what is the correct fix?
AAirflow automatically detects duplicate rows via primary key constraints — duplicate inserts are silently ignored
BWithout idempotency: Task 4 inserts another 50,000 rows, resulting in 100,000 duplicate records in PostgreSQL. Fix: use INSERT INTO ... ON CONFLICT DO NOTHING with a natural unique key, OR use DELETE WHERE batch_date = '{{ ds }}' before inserting (delete-then-insert pattern), OR use TRUNCATE + INSERT on a staging table then MERGE into production
CSet depends_on_past=True on Task 4 — this prevents re-execution if the task already ran successfully in this DAG run
DSet the DAG's max_active_runs=1 — this prevents Task 4 from running while a previous instance is still in the Airflow history
Q16ETL vs ELTMedium
At SmartIMS you designed ETL/ELT pipelines with Snowflake. When would you choose ELT over ETL for an ML feature engineering pipeline, and what is the trade-off?
AELT is always faster than ETL — always use ELT for ML pipelines regardless of context
BChoose ELT when the target warehouse (Snowflake) has more compute power than the transformation layer. Load raw data first, then transform in SQL using Snowflake's compute. Trade-off: raw data (including sensitive PII) lands in the warehouse before masking — requires strong access controls. ETL is better when sensitive data must be masked before it ever touches the warehouse
CELT stands for Extract-Load-Transform — the "T" happens in the target database. This only works for Snowflake, not PostgreSQL or MySQL
DELT is only suitable for batch pipelines — streaming data always requires ETL because real-time transformation must happen before loading
Q17Schema DriftMedium
A source system upstream from your SmartIMS pipeline renames a column from customer_id to cust_id without notice. Your PySpark job fails with a AnalysisException: Column customer_id not found. How do you build resilience against this?
AUse df.select("*") everywhere — selecting all columns means schema changes never cause failures
BImplement schema validation at the source read step: define an expected schema, compare incoming columns against it before processing, and raise an explicit SchemaValidationError with details about the mismatch. Alert on-call immediately rather than propagating corrupt data downstream. Long-term: use a schema registry (Confluent Schema Registry, AWS Glue Data Catalog) to enforce contracts between producer and consumer
CAdd a try/except around the column reference and substitute a default value when the column is missing — pipelines should self-heal silently
DUse df.schema.fields to dynamically find the customer ID column at runtime by matching common patterns like "cust", "customer", "client" — fuzzy column matching prevents failures

Q21Data LineageMedium
